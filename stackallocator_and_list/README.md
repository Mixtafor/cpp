# List and StackAllocator

## Часть 1. StackAllocator

Напишите класс `StackAllocator<typename T, size_t N>`, который позволяет создавать стандартные контейнеры **на стеке**, без единого обращения к динамической памяти. Для этого пригодится класс `StackStorage<size_t N>`, в котором хранится большой массив на стеке. Объект класса `StackAllocator` должен быть легковесным, легко копироваться и присваиваться. Объект `StackStorage`, напротив, **не должен поддерживать копирование**.

`StackAllocator` должен удовлетворять требованиям к аллокатору, описанным на странице:  
<https://en.cppreference.com/w/cpp/named_req/Allocator>  
Он должен быть STL-совместимым, то есть позволять использование в качестве аллокатора для стандартных контейнеров. В частности, должны быть определены:

- Конструктор копирования, деструктор, оператор присваивания;
- Методы `allocate`, `deallocate`;
- Внутренний тип `value_type`;
- Метод `select_on_container_copy_construction`, если логика работы аллокатора этого потребует.

### Пример использования

```cpp
int main() {
    StackStorage<100'000> storage;
    StackAllocator<int, 100'000> alloc(storage);
    std::vector<int, StackAllocator<int, 100'000>> v(alloc);
    // ... useful stuff ...
}
```

Во время исполнения может существовать несколько `StackStorage` с одним и тем же `N`. Разумеется, **аллокаторы, построенные на разных `StackStorage`, должны считаться неравными**.

### Выравнивание (alignment)

`StackAllocator` должен заботиться о выравнивании объектов. Нельзя класть:
- переменные типа `int` по адресам, не кратным 4;
- переменные типа `double` по адресам, не кратным 8;
- и т. д.

### Запрет динамической памяти

Использование **любого** контейнера со `StackAllocator` вместо `std::allocator` должно приводить к тому, что обращений к динамической памяти **не происходит вообще**.

### Производительность: самопроверка

Напишите тестирующую функцию, которая создает `std::list` и выполняет над ним последовательность случайных добавлений/удалений элементов. Если всё сделано правильно, то `std::list` со `StackAllocator` должен работать **быстрее**, чем `std::list` со стандартным аллокатором.

## Часть 2. List (двусвязный список)

Напишите класс `List` — двусвязный список с **правильным использованием аллокатора**. Правильное использование аллокатора означает соответствие требованиям:  
<https://en.cppreference.com/w/cpp/named_req/AllocatorAwareContainer>

Шаблонные параметры:
- `T` — тип элементов в списке;
- `Allocator` — тип используемого аллокатора (по умолчанию — `std::allocator<T>`).

### Требуемая функциональность

- **Конструкторы**: без параметров; от одного числа; от числа и `const T&`; от одного аллокатора; от числа и аллокатора; от числа, `const T&` и аллокатора.  
  Если создается **пустой** список, не должно быть никаких выделений динамической памяти, **независимо** от аллокатора.
- Метод `get_allocator()`, возвращающий объект аллокатора, используемый в списке на данный момент;
- Конструктор копирования, деструктор, копирующий оператор присваивания;
- `size()` (за **O(1)**) и `empty()`;
- `push_back`, `push_front`, `pop_back`, `pop_front`;
- **Итераторы** двунаправленные (**BidirectionalIterator**), а также константные и `reverse`-итераторы; требования:  
  <https://en.cppreference.com/w/cpp/named_req/BidirectionalIterator>
- Методы `begin`, `end`, `cbegin`, `cend`, `rbegin`, `rend`, `crbegin`, `crend`;
- `insert(iterator, const T&)` и `erase(iterator)` — добавление и удаление одиночных элементов.

### Требования к размеру объекта

Если аллокатор является **пустой структурой** (не содержит полей), он **не должен увеличивать** `sizeof(List)`. То есть тривиальный аллокатор как поле списка должен занимать 0 байт (через EBO / empty base optimization).

### Строгая безопасность относительно исключений

Все методы списка должны быть **строго безопасны** относительно исключений. Это означает, что при выбросе исключения из любого метода класса `T` (кроме деструктора) во время произвольной операции **X** над списком, список должен вернуться в состояние **до** начала выполнения **X**, не допустив UB и утечек памяти, и пробросить исключение наверх.  
Можно считать, что **конструкторы и операторы присваивания у аллокаторов исключений не кидают** (часть требований к `Allocator`).

### Производительность: повторная самопроверка

Выполните последовательность случайных добавлений/удалений элементов в `List<int, StackAllocator<int, 100000>>`. Сравните с `List<int, std::allocator<int>>`.  
И ваш собственный `List`, и `std::list` должны показывать **более высокую производительность** со `StackAllocator`, чем со стандартным аллокатором. В контесте это будет проверяться замерами времени выполнения большого количества однотипных операций. Если ваш аллокатор проиграет по времени стандартному, вы **не пройдете тесты**.
